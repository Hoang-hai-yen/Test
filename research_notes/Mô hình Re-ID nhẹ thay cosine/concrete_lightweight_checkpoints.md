# Concrete, Lightweight, Currently-Downloadable Re-ID / Instance-Matching Checkpoints (2024-2026)

Scope note: this file inventories specific, nameable models a developer could actually download today (weights + code), for a build-vs-buy decision on instance-level re-identification/matching. Person/vehicle-specific models (trained on Market1501/MSMT17/DukeMTMC/VeRi776/VehicleID) are flagged PERSON/VEHICLE-SPECIFIC; everything else is GENERAL-PURPOSE.

Context flag: Papers With Code (the canonical SOTA leaderboard site referenced in the task's "suggested sources") was retired by Meta in July 2025; its live leaderboards for Market-1501 etc. are no longer served, though a static GitHub data dump remains. CodeSOTA is cited as a partial successor. This means leaderboard-based comparisons below rely on GitHub READMEs/papers directly rather than a live PwC table. — [Coursera: What Happened to Papers With Code](https://www.coursera.org/articles/papers-with-code); [CodeSOTA PwC alternative](https://www.codesota.com/papers-with-code)

## What are the current lightweight (<50M params) person/vehicle Re-ID checkpoints commonly available/cited as of 2024-2026?

### Takeaway
OSNet (2019) remains the smallest, most CPU-friendly, actively-referenced person-ReID checkpoint family (0.2M–2.2M params) and its repo/weights are still live; FastReID's model zoo mostly ships ResNet50/ResNet50-IBN/ResNet101-IBN baselines (25M–45M params, so technically under 50M) rather than anything smaller; CLIP-ReID and TransReID's default configs use ViT-B/16 (~86M, over budget) but both also support smaller backbones (ViT-Small ~22M for TransReID, ResNet18/34 mentioned as scalable options); SOLIDER-REID's Swin-Tiny backbone (~28M) is the one SOLIDER variant that clears the <50M bar.

### Cited Findings
- OSNet has "only 2.2 million parameters," introduced by Zhou et al. (ICCV'19), using factorised convolutions and omni-scale feature learning — [Omni-Scale Feature Learning for Person Re-Identification (arXiv 1905.00953)](https://arxiv.org/pdf/1905.00953)
- Exact OSNet variant parameter counts from the official Torchreid Model Zoo: osnet_x1_0 = 2.2M, osnet_x0_75 = 1.3M, osnet_x0_5 = 0.6M, osnet_x0_25 = 0.2M, osnet_ibn_x1_0 = 2.2M, osnet_ain_x1_0 = 2.2M; all trained/available for Market1501, DukeMTMC-reID, and MSMT17, downloadable via Google Drive links in the repo — [Torchreid Model Zoo](https://kaiyangzhou.github.io/deep-person-reid/MODEL_ZOO), [KaiyangZhou/deep-person-reid](https://github.com/KaiyangZhou/deep-person-reid)
- OSNet weights are also mirrored on Hugging Face, e.g. `kaiyangzhou/osnet` and a community mirror `kadirnar/osnet_x0_25_imagenet` — [huggingface.co/kadirnar/osnet_x0_25_imagenet](https://huggingface.co/kadirnar/osnet_x0_25_imagenet)
- A third-party STMicroelectronics model zoo also packages OSNet for edge deployment (STM32 boards), evidence it's still considered a go-to "small" ReID model as of recent years — [STMicroelectronics/stm32ai-modelzoo OSNet README](https://github.com/STMicroelectronics/stm32ai-modelzoo/blob/main/re_identification/osnet/README.md)
- FastReID (JDAI-CV) is a toolbox, not a single checkpoint; its Model Zoo provides baselines (BoT, AGW, SBS, MGN) built on ResNet50, ResNet50-IBN, ResNet101-IBN, and SE-ResNet50 backbones, with 15 models each for Market1501/DukeMTMC/MSMT17, 1 model for VeRi (vehicle), 1 for VehicleID, and 1 for VeRi-Wild, all benchmarked on a single V100 GPU — [fast-reid/MODEL_ZOO.md](https://github.com/JDAI-CV/fast-reid/blob/master/MODEL_ZOO.md)
- FastReID also implements a knowledge-distillation module explicitly to produce "a more precise and efficient lightweight model" from these baselines, though no specific distilled-model parameter count was found in the fetched docs — [github.com/JDAI-CV/fast-reid](https://github.com/JDAI-CV/fast-reid)
- The repo shows ~4k GitHub stars / 881 forks, suggesting ongoing community relevance, but the exact "last updated" timestamp was not retrievable from the fetched page (uncertain maintenance recency) — [fast-reid README](https://github.com/JDAI-CV/fast-reid/blob/master/README.md)
- CLIP-ReID (AAAI 2023) offers both a CNN-based and a ViT-B/16-based backbone; pretrained weights for both Person (Market-1501, MSMT17, DukeMTMC-reID, Occluded-Duke) and Vehicle (VehicleID, VeRi-776) ReID are released via Google Drive, with documented training commands (e.g. `python train_clipreid.py --config_file configs/person/vit_clipreid.yml`) — [Syliz517/CLIP-ReID README](https://github.com/Syliz517/CLIP-ReID)
- One web summary reported CLIP-ReID at "approximately 126.6M parameters and 24.14G FLOPs" — this figure could not be independently verified from the arXiv paper's tables in this research pass and should be treated as **uncertain/unverified**; standard ViT-B/16 alone is ~86M params, so 126.6M likely reflects the full CLIP model (image+text encoder) used during training rather than the inference-time image encoder — [CLIP-ReID arXiv 2211.13977](https://arxiv.org/abs/2211.13977) (numbers not confirmed directly from PDF tables in this pass)
- TransReID (ICCV 2021, damo-cv/TransReID) supports multiple ViT variants including `vit_small_patch16_224_TransReID` (ViT-Small) in addition to its default ViT-Base config; exact parameter count for the TransReID ViT-Small variant was not found in a directly-citable source (only that standard ViT-S/16 ≈ 21-22M params by general ViT convention) — [damo-cv/TransReID](https://github.com/damo-cv/TransReID)
- SOLIDER-REID (tinyvision) fine-tunes SOLIDER's self-supervised Swin Transformer backbones (Tiny/Small/Base, using standard `swin_tiny_patch4_window7_224` / `swin_small_...` / `swin_base_...` configs) for person ReID, with semantic weight set to 0.2 in experiments; exact ReID-head parameter counts were not found, but the underlying Swin-Tiny backbone is a well-known ~28M-parameter model — [tinyvision/SOLIDER](https://github.com/tinyvision/SOLIDER), [tinyvision/SOLIDER-REID](https://github.com/tinyvision/SOLIDER-REID)

### Inferences
- For a true CPU-friendly, <50M, per-crop-fast option, OSNet (any variant, 0.2M-2.2M params) is the standout — it is small enough to run comfortably on CPU per-crop, has been stable/unchanged for years, and is still being re-packaged into new edge model zoos (STM32) as of recent releases.
- FastReID's ResNet50-based baselines (~25.6M params, standard ResNet50 count) are a plausible "under 50M but not tiny" middle ground — closer to "similar cost to ResNet50" than to OSNet's near-zero-cost profile — but exact per-checkpoint parameter counts were not published in the fetched MODEL_ZOO.md, so this is an inference from the known ResNet50 architecture size, not a measured figure from the FastReID docs.
- CLIP-ReID and TransReID's headline configs (ViT-B/16, ~86M) exceed the <50M constraint; only their smaller-backbone options (ViT-Small/ResNet18/34) would qualify, and documentation on exact parameter counts for those smaller variants is thin — treat as a config option that exists but is under-documented.
- SOLIDER's Swin-Tiny variant is the most promising SOLIDER-family option under 50M, but this research did not confirm ReID-specific fine-tuned Swin-Tiny weights are actually published (vs. only Small/Base) — needs direct repo inspection to confirm.

### Gaps
- Exact per-checkpoint parameter counts for FastReID's ResNet50/ResNet50-IBN/ResNet101-IBN/SE-ResNet50 baselines were not listed in the fetched MODEL_ZOO.md page (only backbone names/datasets); would need to open the raw table or the FastReID paper directly.
- Could not verify the CLIP-ReID "126.6M params / 24.14G FLOPs" figure against the primary arXiv paper's tables — flagged as uncertain.
- No confirmed exact parameter count for TransReID's ViT-Small config specifically (as opposed to generic ViT-S/16 conventions).
- Could not confirm whether SOLIDER-REID publishes fine-tuned Swin-Tiny (vs. only Small/Base) checkpoints — would require opening the repo's release/checkpoint list directly.
- FastReID's exact last-commit/maintenance date was not retrievable from the fetched content (only stars/forks as an activity proxy).

## What general-purpose lightweight embedding models are commonly used/recommended for instance-level retrieval/matching as of 2024-2026?

### Takeaway
The strongest, best-documented general-purpose lightweight options are Meta's DINOv2 ViT-S/14 (21M params, 2023) and DINOv3 ViT-S/16 (21M params, released Aug 2025) — both explicitly validated for instance-level image retrieval (not just classification) — plus Apple's MobileCLIP / MobileCLIP2 family (11M-125M-param image towers, 2024-2025), which is explicitly benchmarked on retrieval tasks and optimized for on-device latency.

### Cited Findings
- DINOv2-Small is based on ViT-S/14, has ~21M parameters, embedding dimension 384, 6 attention heads, 12 transformer blocks — [DebuggerCafe: DINOv2 Visual Feature Learning](https://debuggercafe.com/dinov2-visual-feature-learning-without-supervision/), [EmergentMind: DINOv2](https://www.emergentmind.com/topics/dinov2)
- DINOv2 shows large gains specifically on instance retrieval benchmarks: "+34% mAP on Oxford Hard" versus prior self-supervised methods, attributed to curated, diverse pretraining data — [EmergentMind: DINOv2](https://www.emergentmind.com/topics/dinov2)
- DINOv3 (Meta, published 2025-08-13, HF integration 2025-08-14) provides a ViT-S/16 model, `facebook/dinov3-vits16-pretrain-lvd1689m`, with a confirmed **21M parameters** per its Hugging Face model card, released under a custom "DINOv3 license" (non-standard — not Apache/MIT, needs review before commercial use) — [huggingface.co/facebook/dinov3-vits16-pretrain-lvd1689m](https://huggingface.co/facebook/dinov3-vits16-pretrain-lvd1689m)
- The DINOv3 HF model card explicitly states the model can be used "on image retrieval using nearest neighbors" without fine-tuning — [huggingface.co/facebook/dinov3-vits16-pretrain-lvd1689m](https://huggingface.co/facebook/dinov3-vits16-pretrain-lvd1689m)
- DINOv3 is trained via teacher-student distillation from a 7B-parameter self-supervised teacher down to smaller student architectures (including ViT-S, and ConvNeXt-Tiny/Small variants also published) — [Lightly.ai: DINOv3 Explained](https://www.lightly.ai/blog/dinov3)
- MobileCLIP (Apple, CVPR 2024) is "a family of efficient image-text embedding models designed for real-time, on-device retrieval and zero-shot classification," using a novel "multi-modal reinforced training" approach — [Apple ML Research: MobileCLIP](https://machinelearning.apple.com/research/mobileclip)
- Measured MobileCLIP / MobileCLIP2 image-tower parameter counts and latency (from the `apple/ml-mobileclip` GitHub repo): MobileCLIP-S0 = 11.4M params / 1.5ms latency; MobileCLIP-S1 = 21.5M / 2.5ms; MobileCLIP-S2 = 35.7M / 3.6ms; MobileCLIP-B = 86.3M / 10.4ms; MobileCLIP-S3 = 125.1M / 8.0ms; MobileCLIP-L/14 = 304.3M / 57.9ms; MobileCLIP-S4 = 321.6M / 19.6ms. MobileCLIP2 (Aug 2025 update) reuses the same S0/S2/B/S3/L/S4 size points with improved ImageNet-1k accuracy (e.g. MobileCLIP2-S0 71.5% vs MobileCLIP-S0 67.8%) — [github.com/apple/ml-mobileclip](https://github.com/apple/ml-mobileclip)
- MobileCLIP checkpoints are downloadable both via a repo script (`get_pretrained_models.sh`) and via a Hugging Face "MobileCLIP/DataCompDR Collection"; code is MIT-licensed but **model weights are under Apple's "ML Research Model TOU"** (a non-standard, likely non-commercial-restrictive license) and training data is CC-BY-NC-ND — flag for licensing review before commercial use — [github.com/apple/ml-mobileclip](https://github.com/apple/ml-mobileclip)
- SigLIP2 (Feb 2025) is a family of multilingual (109-language) vision-language encoders good for image-text/image-image retrieval and usable as a frozen backbone; it outperforms SigLIP1 across zero-shot classification, retrieval, dense prediction, etc., but this research did not find a clearly-marketed "<50M" SigLIP2 variant — the family is typically described at Base (~93M image tower for patch16) and larger sizes — [SigLIP2 docs (HuggingFace Transformers)](https://huggingface.co/docs/transformers/model_doc/siglip2), [arXiv 2502.14786](https://arxiv.org/pdf/2502.14786)

### Inferences
- For a general-purpose, non-reid-specific embedding backbone under 50M params with strong retrieval credentials, DINOv2 ViT-S/14 and DINOv3 ViT-S/16 (both ~21M params, both explicitly validated on retrieval, both same ballpark of compute as "ViT-S/16" i.e. noticeably cheaper than ViT-B/16 but still GPU-friendlier than truly mobile nets) are the two most defensible current recommendations — DINOv3 is newer (Aug 2025) but carries a non-standard license that needs checking; DINOv2 (2023) has a more permissive/well-trodden Apache-2.0-style license and wider community tooling maturity.
- MobileCLIP-S0/S1/S2 (11.4M/21.5M/35.7M image params, sub-4ms latency) are the best-documented options if the deployment target is genuinely mobile/edge (not just "a modern GPU") — but the model-weights license (Apple ML Research Model TOU) is a real constraint to check against the project's use case, unlike DINOv2's more standard license.
- No EfficientNet-based embedding model explicitly evaluated on instance retrieval (as opposed to classification) was surfaced by this research pass, despite a dedicated search — this suggests EfficientNet-family backbones are not currently a live recommendation in the instance-retrieval space (DINOv2/v3 and MobileCLIP families have superseded them in current discourse), though this is an absence-of-evidence inference, not a confirmed negative.

### Gaps
- No <50M-labeled SigLIP2 variant with an explicit parameter count was found — SigLIP2's smallest well-documented size appears to be "Base" (~93M for patch16), putting it likely over the 50M threshold for the image tower alone; unconfirmed exact number.
- No EfficientNet-based (or other CNN-based, e.g. MobileNetV3) embedding model with a specific, named, currently-downloadable checkpoint explicitly evaluated on instance retrieval was found in this research pass — this may be a true gap in current tooling/discourse, or simply not surfaced by the queries used.
- Exact DINOv2 license terms (Apache 2.0 is the commonly cited license from prior general knowledge) were not re-verified with a fresh source in this pass — should be double-checked before build-vs-buy sign-off.
- MobileCLIP2-S1 parameter/latency figures specifically were not listed in the fetched table (only S0/S2/B/S3/S4/L for v2) — possibly S1 was dropped in the v2 lineup; unconfirmed.

## Are there any lightweight models specifically marketed/evaluated for "few-shot verification" or "one-shot matching" as a packaged, ready-to-use tool/library?

### Takeaway
There is no strong current (2024-2026) packaged, production-ready "few-shot instance verification" product analogous to a DeepFace-for-faces equivalent for general objects; what exists is either (a) general-purpose image-similarity/deduplication libraries (Towhee, fastdup) that can be repurposed for matching, or (b) older/small research-grade few-shot *classification* libraries (thuml/few-shot: MatchingNet, ProtoNet, RelationNet) that require reimplementation/retraining rather than being turn-key verification tools.

### Cited Findings
- Towhee is a pip-installable (`pip install towhee`) pipeline framework with 140+ ready-to-use models across CV/NLP/multimodal/audio/medical; its `image-embedding/isc` operator specifically targets instance-level image retrieval, using pretrained weights from the 1st-place solution of the Image Similarity Challenge 2021 (Descriptor Track) — a general-purpose, ready-to-use instance retrieval component (not person/vehicle-specific) — [towhee.io/image-embedding/isc](https://towhee.io/image-embedding/isc), [pypi.org/project/towhee](https://pypi.org/project/towhee/)
- fastdup is a pip-installable tool for "gaining insights from large image/video collections": finding duplicates, near-duplicates, similarity clusters, and anomalies at scale — positioned as a ready-to-use data-quality/similarity tool rather than a verification API per se — [pypi.org/project/fastdup](https://pypi.org/project/fastdup/)
- thuml/few-shot is described as "a lightweight library that implements state-of-the-art few-shot learning algorithms," including MatchingNet (Matching Networks for One-Shot Learning), ProtoNet (Prototypical Networks), RelationNet, and Baseline/Baseline++ — but these are classification-oriented research reimplementations, not a packaged verification product, and the repo/algorithms are from the 2017-2019 era (not new for 2024-2026) — [github.com/thuml/few-shot](https://github.com/thuml/few-shot)
- Recent (2025) work exists on packaging few-shot *classification* as "multi-instance verification" for backbone-agnostic cross-domain transfer, and a lightweight PyTorch Prototypical-Networks implementation using a ViT-Small/16 backbone was updated October 2024 with training/eval scripts and notebooks — but these read as research/tutorial code rather than an installable "library" with a stable API — [arXiv 2507.00401: Few-shot Classification as Multi-instance Verification](https://arxiv.org/pdf/2507.00401)
- Siamese networks are repeatedly cited as the classical architecture underlying one-shot/few-shot verification (originally for signature verification, later face/prescription-pill identification), but the search surfaced only small individual reproduction repos (e.g. `Bahareh527/siamese_fewshot_project`), not a maintained, widely-adopted packaged tool — [PyImageSearch: Building Image Pairs for Siamese Networks](https://pyimagesearch.com/2020/11/23/building-image-pairs-for-siamese-networks-with-python/), [github.com/Bahareh527/siamese_fewshot_project](https://github.com/Bahareh527/siamese_fewshot_project)

### Inferences
- If the goal is "download a tool and get instance-matching working with minimal reimplementation," Towhee's ISC-2021-descriptor-track operator is the closest fit found to a ready-to-use, general-purpose (non-person/vehicle) instance-retrieval component with an installable API — closer to "buy" than "build" on the build-vs-buy spectrum.
- fastdup is better suited to bulk dataset-level dedup/clustering than to a live "is this crop the same instance as that reference crop" verification API, though its underlying similarity embeddings could likely be adapted.
- The "few-shot verification as packaged tool" niche appears genuinely underserved as of this research pass — most hits are either classification-oriented research repos (thuml/few-shot) or one-off reproduction code, reinforcing that a genuine one-shot/few-shot *matching* product (not classification) with strong packaging does not clearly exist yet for general objects.

### Gaps
- Could not confirm whether Towhee's ISC-2021 operator or fastdup ship an explicit parameter count for their underlying embedding models — would need to inspect the specific operator's model card directly.
- No commercial or well-known open-source "few-shot verification as a service/library" product (comparable to DeepFace/face_recognition for faces) was found for general object instance matching; this may reflect a true market gap rather than a search limitation, but could not be fully ruled out within the tool-call budget.
- Did not evaluate AnyLoc or similar "universal place recognition" embeddings that came up peripherally in search results — flagged as a possible adjacent tool worth checking in a follow-up pass but not verified here.

## For any promising candidate, is there a straightforward way to fine-tune it on a small custom paired dataset?

### Takeaway
OSNet (via Torchreid), CLIP-ReID, TransReID, and SOLIDER-REID all ship complete, documented training code and standard loss recipes (cross-entropy + triplet, or CLIP-ReID's two-stage prompt-learning + ID/triplet loss) making them realistic to fine-tune on custom paired data; DINOv2/DINOv3 and MobileCLIP are released primarily as frozen feature extractors with official pretraining code but no turnkey "fine-tune for your own ID-verification pairs" recipe — fine-tuning them for reid-style triplet/contrastive objectives is a "build it yourself on top of the checkpoint" exercise, not a documented out-of-the-box workflow.

### Cited Findings
- Torchreid (OSNet's home repo) is a general person-ReID *training framework*, not just a weights repository — it documents dataset registration, training scripts, and both same-domain and cross-domain training configs in its docs — [KaiyangZhou/deep-person-reid](https://github.com/KaiyangZhou/deep-person-reid), [Torchreid docs](https://kaiyangzhou.github.io/deep-person-reid/)
- CLIP-ReID's README documents concrete training commands, e.g. `python train_clipreid.py --config_file configs/person/vit_clipreid.yml`, with separate CNN-baseline and ViT-based config files, though the README's fetched excerpt did not spell out the exact loss-function formulation in detail — [Syliz517/CLIP-ReID](https://github.com/Syliz517/CLIP-ReID)
- FastReID explicitly supports configurable backbone/head/loss/training-strategy components and includes a knowledge-distillation training path to derive lighter models — indicating a flexible, documented training pipeline (though exact fine-tuning-on-custom-small-dataset documentation depth wasn't directly confirmed) — [github.com/JDAI-CV/fast-reid](https://github.com/JDAI-CV/fast-reid)
- DINOv3's Hugging Face model card documents it as usable "without fine-tuning" for retrieval via nearest-neighbor search on frozen features — it is positioned as a strong off-the-shelf feature extractor rather than something with a documented reid-style fine-tuning recipe in the card itself — [huggingface.co/facebook/dinov3-vits16-pretrain-lvd1689m](https://huggingface.co/facebook/dinov3-vits16-pretrain-lvd1689m)
- MobileCLIP's GitHub repo does provide official training code (per the "training code" release note alongside MobileCLIP2 in August 2025), but this trains the full image-text contrastive model rather than shipping a specific "fine-tune for instance verification pairs" recipe — [github.com/apple/ml-mobileclip](https://github.com/apple/ml-mobileclip)

### Inferences
- The ReID-native models (OSNet/Torchreid, CLIP-ReID, FastReID, TransReID, SOLIDER-REID) are the more "build-friendly" path for a small custom paired dataset precisely because they were designed around exactly this workflow (ID-labeled crops → cross-entropy + triplet loss), with training scripts that expect a Market1501-style folder structure — adapting a small custom paired dataset to that format is realistic engineering work, not research reimplementation.
- The general-purpose embedding models (DINOv2/v3, MobileCLIP) are better understood as strong frozen/zero-shot starting points (good "buy" candidates for a quick baseline via cosine similarity on frozen features) but fine-tuning them specifically for instance verification would require the developer to write their own triplet/contrastive fine-tuning loop on top of the released backbone — a partial "build" even though the backbone itself is "bought."

### Gaps
- Did not directly verify the CLIP-ReID loss function details (the README excerpt fetched did not include the specific loss formulation) — would need to read the paper's method section or the full training config files.
- Did not confirm whether SOLIDER-REID's repo includes a documented workflow for fine-tuning on a *new, small, custom* dataset (as opposed to just reproducing benchmark numbers on Market1501/MSMT17) — this distinction (large benchmark reproduction vs. small custom dataset fine-tuning) was not directly tested in any source found.
- No source was found confirming or denying a documented "few-shot fine-tuning" recipe specifically for MobileCLIP or DINOv2/v3 (i.e., fine-tuning on a handful of paired examples rather than large-scale contrastive pretraining) — this remains an open question likely requiring direct experimentation rather than documentation lookup.
